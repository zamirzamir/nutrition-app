## 0. Что это за продукт (в двух абзацах)

Веб-приложение для фитнес-тренера: клиент вводит пол, вес, рост, возраст, цель (похудеть/
набрать/держать) и уровень активности → приложение считает суточную норму **КБЖУ**
(калории, белки, жиры, углеводы) и строит **персональный план питания на 28 дней** — каждый
день 4–6 приёмов пищи с конкретными рецептами, точными порциями (в граммах) и КБЖУ,
попадающими в норму с точностью ±1.5% по калориям и ±3% по Б/Ж/У. Клиент может листать
блюда (свайп-замена в слоте), исключать ингредиенты, фиксировать («замок») понравившиеся
блюда, отмечать съеденное, получать список покупок.

Монетизация: доступ на 31 день за 299 ₽ через платёжку Продамус. Бесплатная витрина
(`index.html`) показывает расчёт КБЖУ и пробный план как воронку; личный кабинет
(`cabinet.html`) открывается после оплаты и хранит профиль/прогресс на сервере.

Пояснения к полям:
- `meal_type[]` — в какие приёмы годится: `breakfast|lunch|dinner|snack`.
- `ingredients[].id` — это **имя** ингредиента (строка), совпадающее с ключом в
  `ingredients_kbju.json`/`micronutrients.json`. Не числовой id.
- `ingredients[].amount_g` — граммовка в БАЗОВОМ рецепте (на `base_servings` порций).
- Опционально у ингредиента: `fry:true` + `absorb_ratio` (доля впитанного масла, см. §4.1).
- `portions[group]` — **запечённая** готовая порция под каждую из 6 весовых групп:
  вес `g` и КБЖУ `kcal/p/f/c`. Это ключевой ускоритель — движок не пересчитывает базу,
  а берёт готовую порцию группы и масштабирует её.
- `tags.dish_type` — тип блюда для чередования (чтобы не шли 5 оладий подряд).
- `tags.cook_total_min` — время готовки (завтраки ≤20 мин показываются первыми).
- `balance_off` — если `true`, блюдо исключено из авто-подбора (несбалансированное).
- `score/rank/carousel` — ранжирование (запекается офлайн, см. §5).

**Партии id:** `fr_XXXXX` — основная база; `pdf_540XXX` — рецепты из PDF; `vg_/vt_` —
вег/вегетарианские; `fr_9000XX` — добавленные вручную (коктейли, углеводный сэт).

```

## 3. Алгоритм расчёта КБЖУ (точные формулы)

Это ядро. Порядок строгий (утверждён с тренером). Вход: пол, текущий вес `cw`, целевой
вес `tw`, рост `height`, возраст `age`, активность.

**Валидация:** вес ≥30 кг; рост 100–250 см; возраст 10–100; |tw−cw| ≤ 20 кг за цикл.

**Шаг 1 — BMR (Миффлин–Сан-Жеор):**
```
муж:  BMR = 10*cw + 6.25*height − 5*age + 5
жен:  BMR = 10*cw + 6.25*height − 5*age − 161
```

**Шаг 2 — TDEE:** `TDEE = BMR * actFactor`, где активность (по шагам/день):
```
sedentary (<3000)      → 1.20
light     (3000–6000)  → 1.375
moderate  (6000–10000) → 1.55
active    (10000–15000)→ 1.725
```

**Шаг 3 — цель:** `isLoss = tw<cw`, `isGain = tw>cw`, иначе `maintain`.

**Шаг 4 — калории:**
```
похудение: kcal = TDEE * (TDEE>=2200 ? 0.80 : 0.85)   // щадящий дефицит для малоедящих
набор:     kcal = TDEE * 1.10
держать:   kcal = TDEE
```
Округлить. **Физиологический пол калорий:** муж ≥1500, жен ≥1200 (ниже не опускаем).

**Шаг 5 — белок (г).** Коэффициент по цели и активности (`below6000` = sedentary/light):
```
похудение: 1.6 (below6000) / 1.8 (moderate) / 2.0 (active)
набор:     1.8 (below6000) / 2.0 (иначе)
держать:   как похудение
```
База веса: при **ожирении (BMI>30)** белок считаем от среднего веса `(cw+tw)/2`, иначе от `cw`.
Потолок коэффициента 2.0 г/кг. Абсолютный потолок белка **220 г** (выше из обычной еды
не собрать). `protein = round(baseW * coef)`, затем cap 220.

**Шаг 6 — жиры (г):**
```
коэф: муж 0.8(похуд)/0.9(иначе); жен 0.9(похуд)/1.0(иначе); набор всегда 1.0
ожирение: fat = round(coef*tw), cap муж 100 / жен 90
иначе:    fat = round(cw*coef)
пол жира (жёстко для всех): муж ≥60 г, жен ≥55 г
```

**Шаг 7 — углеводы (остаточно):** `carbs = round((kcal − protein*4 − fat*9) / 4)`.

**Шаг 8 — защита углеводов ≥130 г:** пока `carbs < 130` и коэф белка > 1.6 — снижаем
коэф белка шагами 0.1, пересчитываем белок (cap 220) и углеводы. Жиры не трогаем.

**Клетчатка (только показ):** муж 19–50 → 38 г, 51+ → 30 г; жен 19–50 → 25 г, 51+ → 21 г.

**Прогноз:** только рекомендуемый темп (без сроков): похудение «−0,7–1,0 кг/нед»,
набор «+0,3–0,5 кг/нед». (Прогноз по времени убран как психологически вредный.)

> ⚠️ Эти формулы — медицинская логика, согласованная с тренером. При переносе в мобилку
> **не менять числа**. Если хочешь другую модель (напр. Харрис-Бенедикт) — это отдельное
> продуктовое решение, а не рефакторинг.

Путь блюда: базовый рецепт → делим на `base_servings` (1 порция) → двигаем под целевые
калории приёма (гибкость **±20%**) → зажимаем в коридор веса приёма → жёсткие потолки.

Коридоры веса (утв. диетологией):
```
основное блюдо: муж <70→200-350, 70-90→220-400, 90+→250-450
                жен <60→180-300, 60-80→200-350, 80+→220-400
перекус (snack): 50-250 г
суп: 300-500 г
потолок ~1.6× калорий приёма; спец-потолки: орехи 20-30 г, десерты 100-140 г
жёсткий потолок порции: белок ≤40 г (для 80-100 кг), жир ≤ min(50, 40% суточного)
```
Мягкое расширение верхнего потолка веса, если иначе не набрать калории приёма:
муж +20%, жен +15%.

## 5. Движок подбора блюд (сердце системы)

Есть два режима, переключаются флагами:
- **SEED-режим** (`USE_ANCHOR_SEED=true`) — основной. Берёт готовый якорь-пресет и достраивает.
- **Мотор** (движок с нуля) — фолбэк, когда seed не подходит (есть исключения ингредиентов,
  ручной выбор блюд, или под профиль нет якоря).

### 5.1 Выбор якоря (`pickAnchor`)

По профилю считаем целевые доли калорий: `up=p*4/kcal`, `uf=f*9/kcal`, `uc=c*4/kcal`.
Среди якорей своей весовой группы и своего числа приёмов ищем ближайший по сумме модулей
отклонений долей Б/Ж/У. Фолбэк — то же число приёмов, любая группа.

### 5.2 Сборка дня из seed (`_buildDayFromSeed`)

Для дня N берём набор id из `anchor.days[(N-1) % 28]`. По каждому слоту:
берём рецепт по id → `scaleRecipe` под целевые калории слота (доля из `MEAL_KCAL_DIST`) →
собираем день → **`rebalanceDayMacros`** дотягивает день до нормы → применяем «замки» блюд.
Если в дне встречается исключённый ингредиент или блюдо отсутствует → фолбэк в мотор.

### 5.3 Ребаланс дня (`rebalanceDayMacros`) — как достигается ±3%

Цель: калории ±1.5%, Б/Ж/У ±3%. Два механизма:
1. **Подгонка весами** (`reweightKcal`): итеративно множим граммовки порций (в коридоре ±20%,
   не превышая жёсткие потолки), чтобы сумма калорий сошлась.
2. **Замена блюд по худшему макросу**: до 40 итераций. Находим самый «промахнутый» макрос
   (Б/Ж/У), в его слоте перебираем до 400 кандидатов из ранжированного пула, выбираем замену,
   минимизирующую суммарный штраф дня (`_macroPenalty`). Замки/съеденные/выбранные вручную
   блюда не трогаем. Умная остановка: выходим, когда улучшение штрафа < 0.001.

Ключевой инсайт: **соотношение Б/Ж/У внутри блюда нельзя изменить порцией** — можно только
поменять блюдо. Поэтому ребаланс комбинирует «крутить веса» + «менять блюдо».

### 5.4 Ранжирование и разнообразие

- **Рабочая колода** (`workingDeck`): только блюда без `balance_off` и с **белок ≥ 1.2×жир**
  на порции группы (убирает «почти жирные» блюда, из-за которых дневной жир уходил за +3%).
- **Фильтр слота** (`filterRecipes`): по `meal_type`; убираем шоколадки, протеин-концентраты
  (коктейли — только вручную), взаимное исключение супа (суп в обед ⇒ нет супа в ужин).
- **Порядок:** предпочтения клиента → «карусель разнообразия» (запечённый порядок с
  чередованием `dish_type`) → топ-ранг → ранг → score. Карусель/ранги **запекаются офлайн**
  (в консоли видно «Recipe scores from baked data (top-1000 ready)»).
- **Аномалия макросов** (`isMacroAnomaly`): блюдо не предлагаем, если >82% ккал из жира
  или >75% из белка (моно-продукт, порцией не сбалансировать).
- **Разнообразие между днями**: в «использованные» подмешиваются блюда последних 3 дней,
  чтобы день отличался от предыдущих (ротация макро- и микронутриентов).

### 5.5 Как офлайн собираются якоря (скрипты)

Пресеты собираются НЕ в рантайме, а офлайн-скриптами на Python (лежат в проекте):
- `build_super_presets.py` — генерирует 28-дневки под каждый якорь: случайный перебор
  наборов дней из подходящих блюд, отбор по попаданию в ±3% Б/Ж/У, штраф за UL-зашкал
  микронутриентов, бонус за сложные углеводы, жадный отбор 28 дней с максимальным
  разнообразием.
- `fix_poor_anchors.py` — чинит якоря с бедным разнообразием (экстремальный профиль Б/Ж/У):
  прогрессивно расширяет коридор seed'а (±3→±5→±8%), пока не наберётся достаточно разных
  дней. Безопасно: живой движок всё равно дотянет до ±3% под человека. Защита «не ухудшать».
- `validate_presets.py` — проверяет разнообразие/микро/попадание всех 238 якорей.

## 6. Микронутриенты и безопасность (UL)

Помимо КБЖУ система считает 20+ микронутриентов и проверяет **верхние безопасные пределы (UL)**:
- RDA (суточные нормы) и UL заданы таблицами.
- Для токсичных при передозе (витамин A, D, железо, цинк, селен) действует **80% от UL**
  (`UL_SAFE=0.8`), для остальных 100%. Дни, где сумма превышает `ULcap`, отбраковываются
  при сборке пресетов.
- Микро-скоринг дня: сумма `min(нутриент/RDA, 1.0)` по «полезным» полям — максимизируется
  при отборе (чем полнее покрытие, тем лучше).

Это защита реального здоровья (напр. печень = витамин A: блюда с печенью ограничены по порции
и частоте). При переносе в мобилку сохранить UL-проверку.

## 7. Взаимодействия клиента

- **Исключение ингредиентов** (категории + конкретные названия): при наличии исключений
  seed-режим выключается, работает мотор (он умеет обходить запреты заменой). Реализована
  логика «исключить любой ингредиент целиком» (напр. «рисовая мука» не разбивается на
  «рис»+«мука»). Есть замок-фиксация списка исключений.
- **Свайп-замена блюда**: клиент листает блюда в слоте, день выправляется ребалансом
  (`lockedIdx` — свайпнутое блюдо не заменяют, только веса крутят).
- **Замок блюда** (`_lockedDishes`): фиксирует блюдо на день/слот, переживает перезаход
  (хранится в прогрессе на сервере). Красный замок = закрыт.
- **Съеденное** (`_eatenCards`): отмеченные блюда «заморожены» (вес не меняется).
- **Список покупок**: агрегирует ингредиенты по дням (с полным количеством масла).
- **Голосовой/текстовый подбор**: «хочу протеин», «добавь блюдо» и т.п.

## 8. Бэкенд, оплата, доступ (точно)

**Стек:** одна Yandex Cloud Function (Node.js) как роутер + YDB serverless + API Gateway.
`API_BASE` = адрес API Gateway. Все запросы с `credentials:'include'` (кука) и/или
`Authorization: Bearer <token>`.

**Таблицы YDB (ключ = email):**
```
subscriptions(email PK, phone, prodamus_order_id, paid_at, expires_at, updated_at)
user_profiles(email PK, data, locked, created_at, updated_at)
user_progress(email PK, data, updated_at)
```

**Эндпоинты:**
```
POST /prodamus-webhook  — приём оплаты: UPSERT подписки по email (+order_num, +31 день)
POST /login-verify      — вход { email, code }, code = номер заказа → ставит куку/токен
GET  /check             — гейт: валидна ли кука + активна ли подписка → { ok, email, expires }
POST /profile-get|save  — профиль клиента
POST /progress-get|save — прогресс (зачёркнутые дни, съеденное, замки)
```

**Модель доступа:** `ACCESS_DAYS = 31`. Кука подписана HMAC: `email.expires.HMAC`.
Вход = **email + номер заказа Продамуса** (никаких SMS/OTP). `login-verify` проверяет, что
введённый код равен `prodamus_order_id` из подписки, и что подписка активна.

**Продление (важно!):**
```
новый_срок = max(старый_срок, сейчас) + 31 день
```
То есть оплата в середине месяца НЕ сгорает — новый месяц клеится в конец. При каждом платеже
`prodamus_order_id` **перезаписывается новым** → поэтому после продления **старый номер заказа
перестаёт пускать, входит только новый**. Это by design.

**Гейт рецептов:** `GET /recipes-url` может вернуть временную ссылку на recipes.json, если
оплата активна (иначе локальный файл). Профиль/прогресс синхронизируются на сервер.

**Оплата (Продамус):** ведём на ГОТОВУЮ страницу оплаты (короткая ссылка `payform.ru/74bSKMr`),
НЕ на корень домена (корень открывает пустую форму). Email клиент вводит на самой странице
Продамуса; вебхук привязывает продление к этому email. После оплаты клиент получает письмо
с номером заказа = кодом входа.

## 9. Хостинг, деплой, PWA

**Хостинг:** статика в бакете Yandex Object Storage `roman-nutrition-app`, раздача как сайт.
Заливка через `aws s3 cp/sync` (профиль `ycloud`, ключи в `~/.aws`, не в коде). HTML — с
`no-cache`; JSON — `no-cache`; фото — кэшируемые. `deploy.sh` делает бэкап, заливает,
сверяет MD5 залитого. **Фото заливаются отдельно** (`aws s3 sync dish_photos/`).

**PWA:** `manifest.json` (standalone, иконки 192/512), `start_url=/cabinet.html`.
**Тихое авто-обновление:** в HTML запечена `APP_VERSION` (метка деплоя, ставит `deploy.sh`),
рядом лежит `version.json` (no-cache). Клиент при открытии сверяет версию и, если вышла новая,
сам перезагружается с cache-buster `?v=`. Так установленный PWA не застревает на старой версии.

## 10. Офлайн-пайплайн добавления рецептов (важно для контента)

Правила проекта (соблюдать строго):
1. **Рецепты только из интернета** — реальные, кем-то приготовленные и проверенные. Сами
   НЕ выдумываем. Находим источник, переписываем текст оригинально (названия/шаги).
2. **Никаких «варёных» продуктов в базе.** Вся варка — в шагах, через сырой продукт + воду.
   Пример: не «кускус варёный 200 г», а «кускус сухой 70 г + вода 130 г» + шаг «залить».
   Иначе врут и вес блюда, и КБЖУ.

Скрипты:
- `add_recipe.py` — принимает рецепт (сырьё + граммы), считает `portions` по 6 группам,
  микронутриенты по порциям, прогоняет валидацию.
- `fix_cooked_grains.py` — переводит «варёные крупы/пасту» на модель «сырое + вода»
  калорий-нейтрально: `dry_g = cooked_g × cooked_kcal/dry_kcal`, `water_g = cooked_g − dry_g`.
- Пересчёт `micronutrients_per_portion.json` после любых правок.

**Генерация фото (Higgsfield MCP):** модель `nano_banana`, соотношение 21:9, 1 кредит/фото.
Промт по составу блюда → job → CDN-ссылка PNG → конвертация в webp (quality 82) → имя строго
`<id>.webp` → положить в `dish_photos/` → прописать `image_url` → залить sync. Конвертация
PNG→webp делается через Pillow (не через Mac `sips` — он молча не пишет webp в этом окружении).
**Верификация фото:** субагенты сверяют каждое фото с рецептом (совпадает/минор/mismatch).

## 11. Сложности, которые уже встречались, и как их решали (учиться на них)

- **Дневной жир вылезал за +3%** — 2-3 «почти жирных» блюда (Ж≈Б) в день. Решение: колода
  только с белок ≥ 1.2×жир.
- **Свайп ломал день** при многих заменах подряд у лёгких женских профилей (узкие порции):
  клиент мог свайпнуть на блюдо с плохим составом, а порция это не чинит. Решение: фильтр
  свайпа по всем 3 макросам + предупреждение о тупике.
- **Бедные якоря** (экстремальный профиль Б/Ж/У почти не собирался): прогрессивное расширение
  seed-коридора + защита «не ухудшать» + маркер попыток для возобновляемости.
- **Специи зашкаливали микронутриенты** (корица, мускат, гвоздика, сода) — резали порции
  точной формулой водопоглощения `new = limit*S/(P−limit)` с запасом 3%.
- **Печень → витамин A за UL** — ограничили порции и частоту.
- **Варёный кускус/крупы в базе** — врали вес и КБЖУ; перевели всё на «сырое + вода».
- **Продление подписки**: сначала непонятно было, стыкуется ли срок. Подтверждено: стыкуется
  (`max(старый,сейчас)+31`), старый номер заказа отваливается (перезапись `prodamus_order_id`).
- **Продамус открывал пустую форму** — вели на корень домена; фикс: вести на готовую
  короткую ссылку страницы 299 ₽.
- **Замки слетали на днях 2-28 после перезагрузки** — не применялся `applyLockedDishes` в
  ветке серверного плана; починили в `renderDayMeals`.
- **PWA застревал на старом кэше** — добавили тихий апдейт через `version.json` + `APP_VERSION`.

## 12. Что переиспользовать в мобилке, а что переделать

**Переиспользовать 1-в-1 (портировать логику):**
- Весь расчёт КБЖУ (§3) — чистые формулы, никакой платформенной специфики.
- Движок подбора: `pickAnchor`, `_buildDayFromSeed`, `scaleRecipe`, `rebalanceDayMacros`,
  ранжирование, коридоры/потолки, UL-проверка (§4–6).
- Данные `recipes.json` / `ingredients_kbju.json` / `micronutrients.json` / `anchors_seeds.json`
  — положить в ассеты приложения (офлайн-first). Фото — в CDN или ассеты.
- Модель доступа и продления (§8) — бэкенд можно оставить тот же (мобилка ходит на тот же
  API Gateway), меняется только клиентская часть авторизации.

**Переделать под платформу:**
- UI/рендер (в вебе — прямые манипуляции DOM; в мобилке — нативные списки/экраны). Учесть,
  что полный рендер 28 дней тяжёлый — рендерить по дню/лениво.
- Оплата: в мобильных сторах (App Store/Google Play) свои правила на цифровые подписки
  (обычно требуется встроенная покупка IAP, а не внешняя платёжка). Это отдельное решение:
  либо IAP, либо веб-оплата вне приложения. Продамус в его текущем виде для сторов не подойдёт.
- Хранение прогресса: тот же серверный API или локальная БД + синк.
- Тихий апдейт: в сторах обновления идут через сам стор; версионирование данных (recipes и т.п.)
  можно оставить через `version.json`-подобный механизм для контента.

**Что уточнить у владельца перед стартом мобилки:**
1. Платформа и стек (нативный iOS/Android, React Native, Flutter)?
2. Оплата: IAP или внешняя веб-оплата?
3. Офлайн-режим обязателен? (если да — все данные в ассеты, сервер только для доступа/синка)
4. Переносим ли текущую базу клиентов (email+подписки) или старт с нуля?
